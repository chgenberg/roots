SCOUT 7 — Login flow (/login + auth API)
================================================================
Date: 2026-05-25
Scope: apps/web/src/app/(auth)/login/*, apps/api/src/routes/auth.ts (login/logout/me),
       apps/api/src/lib/session.ts, apps/api/src/lib/rate-limit.ts, apps/api/src/lib/password.ts

NOTE: Scout brief referenced `/logga-in`; the live route is `/login` only. No `/logga-in`
redirect exists in next.config or the web app — but email templates still link there.

SUMMARY
-------
Core login works for DB-backed users: form validation, CSRF-protected POST, argon2 verify,
httpOnly session cookie, role-based client redirect, unified 401 copy, and audit events on
the DB path. MVP-blocking gaps: welcome emails link to a non-existent `/logga-in` path,
forgot-password is entirely absent, in-memory demo logins land with `orgId: null` (fundraising
403), and rate-limit / already-logged-in / `?next=` UX are incomplete.
Findings: 19 (P1:3 P2:6 P3:6 P4:4)
MVP readiness: 68/100

P1 — CRITICAL

[1.1] Welcome email CTA links to `/logga-in` — route does not exist
  File: apps/api/src/lib/email/templates.ts:61
  Symptom: Post-registration welcome mail button href is `${siteUrl()}/logga-in`. Web app serves login at `/login` only; no redirect in next.config.ts.
  Root cause: Swedish URL slug never wired; templates not updated when route settled on `/login`.
  Fix: Change to `/login` or add permanent redirect `/logga-in` → `/login` in next.config.
  Effort: S

[1.2] Forgot password completely missing from product
  File: apps/web/src/app/(auth)/login/page.tsx (no link)
        apps/api/src/trpc/routers/auth.ts:105-113 (stub returns success, sends nothing)
        apps/api/src/routes/auth.ts (no REST reset endpoint)
  Symptom: No "Glömt lösenord?" on login. tRPC `requestPasswordReset` is a no-op stub ("If the email exists, a reset link was sent") with no email, token table, or UI entry point.
  Root cause: Password reset never implemented beyond placeholder; login page never linked.
  Fix: Add link on login → request form; implement token + email + set-password route on REST (or wire tRPC + page); until then show honest "Kontakta support" copy.
  Effort: L

[1.3] In-memory demo logins set orgId:null — fundraising dashboards 403
  File: apps/api/src/routes/auth.ts:68-73,199-220
  Symptom: `forening@demo-if.se` / `lag@demo-if.se` (and other demo emails when DB miss) authenticate but session has `orgId: null`. Fundraising layout/API returns 403 "Ingen organisation" unless `pnpm db:seed:demo` created real rows.
  Root cause: Demo fallback intentionally skips DB; comment in auth.ts acknowledges gap but UX gives no warning at login.
  Fix: Prefer DB-seeded demo users in staging; or block demo fundraising roles without orgId with clear login error; or show post-login banner "Kör db:seed:demo".
  Effort: M

P2 — HIGH

[2.1] Login page ignores `?next=` deep-link from middleware
  File: apps/web/src/middleware.ts:111-113,126-128
        apps/web/src/app/(auth)/login/page.tsx:44-53
  Symptom: Protected `/forening`, `/lag`, `/min-shop` redirect to `/login?next=…` but successful login always hard-redirects by role, never reads searchParams.
  Root cause: Post-login router.push fixed map; no useSearchParams.
  Fix: After role check, if safe relative `next` param present and allowed for role, router.push(next) else default map.
  Effort: S

[2.2] Already-authenticated users can still open `/login`
  File: apps/web/src/app/(auth)/login/page.tsx; apps/web/src/app/(auth)/layout.tsx
  Symptom: No mount-time `/v1/auth/me` check; logged-in user sees login form until they navigate away.
  Root cause: Auth layout is static chrome only; unlike portal/fundraising layouts.
  Fix: Client effect: if me.user, redirect to role home (same map as post-login).
  Effort: S

[2.3] Rate limit hit — no Retry-After or countdown for user
  File: apps/api/src/routes/auth.ts:106-111
        apps/api/src/lib/rate-limit.ts:34-40
        apps/web/src/app/(auth)/login/page.tsx:39-41
  Symptom: 5 attempts / 15 min per IP+email; API returns generic Swedish 429 without `resetInSeconds` in body or `Retry-After` header. UI shows static error string.
  Root cause: loginRateLimit computes TTL but handler discards it on 429 response.
  Fix: Include `{ retryAfterSeconds: rl.resetInSeconds }` in 429 JSON + optional header; login page countdown timer.
  Effort: S

[2.4] Demo login audit gaps — false failed event, no success event
  File: apps/api/src/routes/auth.ts:194-197,210-220
  Symptom: `auth.login.failed` (reason: no_user) fires before demo fallback even when demo password will succeed. Successful demo login never emits `auth.login.success`.
  Root cause: Audit block placed between DB miss and demo branch; demo path has no auditLog call.
  Fix: Move failed audit after demo rejection; add success audit for demo with meta.demo=true.
  Effort: S

[2.5] `/portal/*` not middleware-protected — client-only auth gate
  File: apps/web/src/middleware.ts:17-21 (PROTECTED_ROUTES excludes /portal)
        apps/web/src/app/(portal)/portal/layout.tsx:111-122
  Symptom: Unauthenticated visitor can load portal shell HTML/JS briefly; relies on client fetch to /me then replace to /login. API routes still enforce auth server-side.
  Root cause: Historical split — fundraising routes in middleware, B2B portal not.
  Fix: Add `/portal` to middleware with role allowlist (CLUB_*, SALES_*, INTERNAL_ADMIN) or server-side redirect in portal layout server component.
  Effort: M

[2.6] Role redirect map incomplete vs scout brief
  File: apps/web/src/app/(auth)/login/page.tsx:44-53
  Symptom: CLUB_ADMIN / SALES_REP / INTERNAL_ADMIN → `/portal` (OK). SELLER → `/min-shop` (fundraising seller shell, not `/portal/saljare` which is admin roster). ASSOCIATION_ADMIN → `/forening`, TEAM_LEADER → `/lag`.
  Root cause: Two product surfaces (B2B portal vs fundraising); brief assumed single portal path.
  Fix: Document as intentional OR add SELLER branch if product wants seller under /portal (currently no seller nav in portal layout).
  Effort: S (doc) / M (route change)

P3 — MEDIUM

[3.1] Rate limit fails open when Redis unavailable
  File: apps/api/src/lib/rate-limit.ts:29-31
  Symptom: Redis error → `{ allowed: true }` — unlimited login attempts during outage.
  Root cause: Deliberate availability trade-off.
  Fix: In production, fail closed or use in-memory fallback with lower cap; alert on Redis down.
  Effort: M

[3.2] `/me` returns session role with empty identity if DB user deleted
  File: apps/api/src/routes/auth.ts:381-416
  Symptom: Valid Redis session + missing users row (and no demoProfile) → `{ user: { email: "", name: "", role, orgId, userId } }` instead of `{ user: null }`.
  Root cause: Session trusted when DB lookup returns nothing and no demoProfile.
  Fix: If !user && !session.demoProfile, destroy session and return user:null.
  Effort: S

[3.3] No demo-account panel on login when demos enabled
  File: apps/web/src/app/(auth)/login/page.tsx
        apps/api/src/routes/auth.ts:34-36
  Symptom: Staging with ROOTS_ENABLE_DEMO_ACCOUNTS=true gives no UI hint; operators must read docs/smoketest for emails/passwords.
  Root cause: Demo credentials live only in API constant and seed scripts.
  Fix: When NEXT_PUBLIC_SHOW_DEMO_ACCOUNTS=true, render collapsible "Demokonton" card with emails + Demo1234! + "Endast demo/staging" badge.
  Effort: S

[3.4] Argon2 parameters duplicated and inconsistent
  File: apps/api/src/routes/auth.ts:38-43 (memoryCost 19456, timeCost 2)
        apps/api/src/lib/password.ts:3-7 (memoryCost 65536, timeCost 3)
  Symptom: Registration/login in auth.ts uses inline ARGON2_OPTIONS; password.ts helper unused by REST login path. Future import of hashPassword from password.ts would produce incompatible hashes.
  Root cause: Parallel implementations during sprint work.
  Fix: Single shared argon2 config module; auth routes import hash/verify from password.ts.
  Effort: S

[3.5] Parallel dead tRPC login router
  File: apps/api/src/trpc/routers/auth.ts:14-54
  Symptom: tRPC `auth.login` has empty `demoUsers` — always UNAUTHORIZED. Web uses REST `/v1/auth/login` (working). Middleware uses tRPC `auth.me` (working via session context).
  Root cause: Legacy stub not removed.
  Fix: Delete or delegate tRPC login to REST; prevents accidental client wiring.
  Effort: S

[3.6] Registration endpoints lack password strength vs password.ts policy
  File: apps/api/src/routes/auth.ts:446-448,563-565,729-731
        apps/api/src/lib/password.ts:31-41
  Symptom: Register association/team-leader/seller only checks presence; no min length on API (UI may vary). change-password enforces 8 chars; password.ts recommends 12.
  Root cause: Strength check not wired on register paths (out of login scope but affects first login).
  Fix: Call isPasswordAcceptable on register bodies; align copy with login-adjacent flows.
  Effort: S

P4 — LOW

[4.1] Logout deleteCookie omits secure/sameSite flags
  File: apps/api/src/routes/auth.ts:246
        apps/api/src/lib/session.ts:97-103
  Symptom: setCookie uses SESSION_COOKIE_OPTIONS; deleteCookie only `{ path: "/" }`. Some browsers may not clear cross-site cookie without matching attributes.
  Root cause: Hono deleteCookie minimal options.
  Fix: Pass same path, secure, sameSite as setCookie.
  Effort: S

[4.2] No post-login welcome or last-visit messaging
  File: apps/web/src/app/(auth)/login/page.tsx:44-53
  Symptom: Immediate silent redirect; conversion audit noted missed retention moment.
  Fix: Optional toast on destination layout ("Välkommen tillbaka, {name}").
  Effort: S

[4.3] tRPC auth errors in English vs Swedish login copy
  File: apps/api/src/trpc/routers/auth.ts:19,34,42
  Symptom: Middleware/auth consumers may surface English TRPCError messages; login form uses Swedish API errors only via REST.
  Fix: Swedish messages on tRPC auth procedures or unified error mapper.
  Effort: S

[4.4] Site preview gate runs before login page
  File: apps/web/src/middleware.ts:78-92
  Symptom: First visit to `/login` may show preview-gate unless `roots_preview` cookie set — extra step for all auth testing.
  Root cause: Intentional pre-launch gate.
  Fix: Document for QA; optional bypass env for E2E.
  Effort: S

WHAT WORKS (no action required for MVP core path)
-------------------------------------------------
- Login form: email + password, autoComplete="email" / "current-password", required fields (login/page.tsx:71-91).
- Submit UX: loading spinner, disabled button, role="alert" errors (login/page.tsx:94-107).
- REST login: CSRF via apiFetch, credentials:include, JSON body (lib/api.ts + app.ts CSRF middleware).
- Credential privacy: DB bad password and unknown user both return 401 "Felaktig e-post eller lösenord." (auth.ts:134,223).
- Session cookie: httpOnly, secure in production, SameSite none (prod) / lax (dev), 7-day maxAge (session.ts:94-103).
- DB login audit: auth.login.success / auth.login.failed with IP + userAgent in meta (auth.ts:129-133,171-175).
- Logout: POST /v1/auth/logout destroys Redis session, deleteCookie, audit auth.logout; portal/fundraising use apiFetch (auth.ts:226-247; portal/layout.tsx:125-129).
- /me: 200 + { user: null } without cookie; populated user with email, role, name, orgName, orgId, userId when session valid (auth.ts:363-420).
- Demo accounts gated: off in production unless ROOTS_ENABLE_DEMO_ACCOUNTS=true (auth.ts:34-36, .env.example).
- change-password: rejects demo sessions explicitly (auth.ts:277-281).
