P1 — CRITICAL (blocks MVP / revenue trust)

[1.1] Kassa total omits shipping fee that API adds for hemleverans
  File: apps/web/src/app/(shop)/shop/[slug]/kassa/page.tsx:92–95,240–244
        apps/api/src/routes/checkout.ts:168–187
  Symptom: Supporter selects “Hemleverans” and sees “Totalt att betala X kr” in summary. If subtotal is below `campaign.shippingThresholdOre`, API adds `shippingFeeOre` to Klarna `orderAmount` but UI never shows frakt row — supporter pays more than displayed on Roots step.
  Root cause: `subtotalOre` / `vatOre` computed from product lines only; no fetch/use of `campaign.shippingFeeOre` / `shippingThresholdOre` from shop payload (shop API returns them; kassa `CheckoutShop` type omits them).
  Fix: Extend kassa shop fetch type; when `deliveryType === "DIRECT"` and subtotal < threshold, show “Frakt” line + update total/VAT display to match server before Klarna redirect.
  Effort: S
  Ref audit: SUPPORTER [2.4] — STILL UNRESOLVED

[1.2] Server accepts DIRECT delivery without shipping address
  File: apps/api/src/routes/checkout.ts:66–68,206–210
        apps/web/src/app/(shop)/shop/[slug]/kassa/page.tsx:116–120
  Symptom: Client sends `deliveryType: "DIRECT"` with empty/null address fields (API call bypass, tampered request, or race). Order persists with `shippingAddressLine1/city/postalCode = null` and proceeds to Klarna.
  Root cause: Validation checks `sellerSlug`, `customerName`, `customerEmail`, `items` only — no conditional require for DIRECT address fields; no email format check.
  Fix: When `deliveryType === "DIRECT"`, return 400 if any of `shippingAddressLine1`, `shippingCity`, `shippingPostalCode` missing/blank; optionally validate Swedish postal format.
  Effort: S
  Ref audit: SUPPORTER [3.11] pattern — server-side gap

[1.3] Klarna session failure leaves FAILED orders with no idempotent retry
  File: apps/api/src/routes/checkout.ts:231–257,195–229
        apps/web/src/app/(shop)/shop/[slug]/kassa/page.tsx:127–129
  Symptom: User sees “Betalningen kunde inte initieras.” and clicks “Gå till betalning” again → new DRAFT/PENDING order each time; prior order stuck FAILED. DB accumulates orphan orders; supporter may double-pay if Klarna eventually succeeds on a later attempt.
  Root cause: Each POST always inserts new `customer_orders` row before Klarna call; no reuse of FAILED draft for same cart fingerprint/session.
  Fix: Reuse existing FAILED/PENDING draft for same seller+customer+items within TTL, or expose `orderId` retry endpoint; surface “Försök igen” with same order when status FAILED.
  Effort: M
  Ref audit: CONVERSION trust at payment commitment

================================================================
THREE FLOWS — WALKTHROUGH
================================================================

FLOW A — Happy path (supporter completes purchase)
1. `/shop/{slug}` — add products via sticky cart (sessionStorage + URL params on link).
2. `/shop/{slug}/kassa?item_{uuid}=qty` — summary shows names/prices/VAT; fill name + email; choose delivery; accept legal copy implicitly; click “Gå till betalning”.
3. POST `/v1/checkout/create` — validates campaign ACTIVE, prices from DB, creates order DRAFT→PENDING, returns Klarna `htmlSnippet`.
4. Klarna widget (or mock “Simulera betalning” when credentials unset) → confirmation URL `/shop/{slug}/bekraftelse?order_id=…`.
5. GET `/v1/checkout/confirm/:orderId` — polls Klarna; status PAID → thank-you + masked email.
**Blockers on happy path:** shipping total mismatch ([1.1]) if hemleverans + below threshold; otherwise works in dev mock mode.

FLOW B — Validation errors
- **Client:** HTML5 blocks empty name/email; DIRECT address fields `required` when visible. No inline Swedish copy beyond browser defaults.
- **Server:** Missing fields → 400 “Alla obligatoriska fält krävs.”; bad qty → “Ogiltig vara…”; inactive campaign → “Kampanjen är inte aktiv.”; unknown product → “Produkt hittades inte: {id}”.
- **UI:** All mapped to single red banner — user must guess cause ([2.1]).
- **Gap:** DIRECT without address via API succeeds ([1.2]); invalid email string accepted server-side ([3.5]).

FLOW C — Payment failure / abandon
- **Klarna API error on create:** Order updated to FAILED; UI “Betalningen kunde inte initieras.” ([1.3] orphan order on retry).
- **Network/CSRF:** “Kunde inte nå servern.” / 403 after token refresh path in apiFetch.
- **User cancels in Klarna:** Redirect to `/shop/{slug}/kassa` without cart params — empty cart, no cancelled message ([2.9]).
- **Bekräftelse with FAILED/CANCELLED:** Error card, no contact link ([2.10]); PENDING shows spinner “Din betalning behandlas…” (acceptable).

================================================================
VAT VERIFICATION
================================================================
Inclusive 25% moms (hygienprodukter):
- UI:  `vatOre = Math.round(subtotalOre * 25 / 125)` — CORRECT for VAT portion of gross.
- API: `taxAmount = Math.round(lineTotal - lineTotal / 1.25)` — equivalent.
- Klarna: `tax_rate: 2500` (25.00%) with amounts in öre — CORRECT.
- Note: Shipping line uses same 25% extraction when added server-side; UI must include shipping in gross before VAT display matches ([1.1]).

================================================================
SCHEMA NOTES (customer-orders.ts)
================================================================
- Status lifecycle: DRAFT → PENDING → PAID (webhook/confirm) | FAILED (Klarna create fail) — matches checkout.ts usage.
- `paymentMethod` enum includes DIRECT_TO_LEADER but checkout always writes KLARNA — product/schema drift ([2.3]).
- Shipping stored as `shippingOre` on order; not broken out on kassa UI.
- No `vatOre` column — VAT derived at payment layer only (OK for Klarna).
