SUMMARY
-------
Schema is structurally sound for core commerce (campaigns → teams → sellers →
customer_orders) with additive migrations 0001–0006 and a consistent journal.
The highest MVP risks are (1) Fas 6 privacy/minor columns exist in DB but have
zero read/write paths in application code, (2) guardian_user_id lacks the FK
MASTER_PLAN specifies, and (3) several Drizzle-declared indexes were never
emitted to SQL (partially patched in 0004, but orders_created_at_idx and
quotes_status_idx remain missing). audit_logs is append-only and now written,
but has no indexes for the admin/notifications query patterns — a scaling
blocker once Fas 5 audit volume ramps up.
Findings: 22 total (P1: 3, P2: 10, P3: 7, P4: 2)
MVP readiness: 68/100

P1 — CRITICAL (MVP-blocking)
================================================================

[1.1] Fas 6 schema columns are dead — minor consent & seller privacy unenforced
  Files: packages/db/src/schema/users.ts:33-35; sellers.ts:43-45;
         apps/api/src/routes/auth.ts:762-780; apps/api/src/routes/shop.ts:85-86
  Symptom: DB has birth_year, guardian_user_id, guardian_consent_at,
    public_alias, hide_from_leaderboard, personal_message but no API route
    reads or writes them. Public shop always exposes real displayName.
  Root cause: Migration 0001 landed schema ahead of Fas 6 application work
    (MASTER_PLAN §263–284). Scout 10 confirmed same gap.
  Fix: Wire register/seller + shop snapshot + leaderboard to columns; not a
    schema change — but schema without app = compliance MVP blocker for
    youth fundraising product.
  Effort: L (app, not DB)
  Ref: MASTER_PLAN Fas 6; Scout 10 [1.2], [2.6]

[1.2] guardian_user_id missing FK to users(id)
  Files: packages/db/src/schema/users.ts:34 (plain uuid, no .references());
         packages/db/drizzle/0001_minor_consent_and_seller_privacy.sql:6-10
  Symptom: Index exists but no referential integrity; invalid guardian UUIDs
    can be stored; deleting a guardian user leaves dangling references with
    no ON DELETE policy.
  Root cause: 0001 added column + index only; MASTER_PLAN explicitly requires
    `guardianUserId uuid null → users.id`.
  Fix: New idempotent migration:
    DO $$ … ADD CONSTRAINT users_guardian_user_id_fk
      FOREIGN KEY (guardian_user_id) REFERENCES users(id) ON DELETE SET NULL;
    Add `.references(() => users.id, { onDelete: "set null" })` in Drizzle
    (self-ref — may need `(): AnyPgColumn` pattern).
  Effort: S
  Ref: MASTER_PLAN Fas 6 schema list

[1.3] audit_logs has zero indexes — admin UI will degrade as Fas 5 logging rolls out
  Files: packages/db/src/schema/audit.ts:3-11;
         apps/api/src/routes/admin.ts:97-113 (ORDER BY created_at DESC);
         apps/api/src/routes/notifications.ts:296-303
  Symptom: Every audit list / notification poll scans full table.
  Root cause: 0000 created bare table; no follow-up migration.
  Fix: Additive migration with IF NOT EXISTS:
    - audit_logs_created_at_idx ON (created_at DESC)
    - audit_logs_action_created_at_idx ON (action, created_at DESC) — optional
    - audit_logs_user_id_created_at_idx ON (user_id, created_at DESC) WHERE user_id IS NOT NULL
  Effort: S
  Ref: MASTER_PLAN Fas 5 (audit_logs write path); T6
