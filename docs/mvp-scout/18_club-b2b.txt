SUMMARY
-------
Portal B2B ordering partially works via REST (`POST /v1/portal/orders`), dashboard KPIs
fetch live data, fakturor/beställningar list orders with CSV export, and member invite
creates DB rows. MVP-blocking gaps: produkter→beställningar cart is disconnected;
order dialog always shows success on failure; fallback SKUs use fake IDs that persist
0 kr ghost orders; no delivery address / PO on orders; recurring subscriptions have no
UI or org-scoped API; invited members cannot accept or log in; Fortnox invoicing is not
wired for club orders (webhook stub); order-status UI maps the wrong field.
Findings: 22 (P1:8 P2:9 P3:4 P4:1)
MVP readiness: 42/100

P1 — CRITICAL (blocks MVP)

[1.1] Produkter → beställningar drops cart — multi-SKU flow broken
  File: apps/web/src/app/(portal)/portal/produkter/page.tsx:165-181
  Symptom: User picks quantities on `/portal/produkter`; sticky bar navigates via
  `window.location.href = "/portal/bestallningar"` with no query, sessionStorage, or POST.
  Cart state is page-local `useState` — selections vanish on navigation.
  Root cause: No shared cart bridge between catalog and order dialog.
  Fix: Pass cart via sessionStorage/URL params, or merge ordering into produkter page,
  or open PortalOrderDialog pre-filled from catalog state.
  Effort: M
  Ref audit: CLUB_MEMBER [1.5] — STILL UNRESOLVED

[1.2] Order submit always shows success — failures silent to user
  File: apps/web/src/app/(portal)/portal/bestallningar/page.tsx:141-183
  Symptom: `handleSubmit` catches API errors (console only) then unconditionally runs
  `setSubmitted(true)` and clears cart. User sees "Beställning skickad!" even when
  `portalFetch` threw (401, 400 org missing, network error).
  Root cause: Success UI not gated on `created.order`.
  Fix: Only set `submitted` when response contains order; show toast/alert on failure;
  keep cart on error.
  Effort: S
  Ref audit: new (regression risk in Sprint E12 work)

[1.3] Fallback catalog IDs create 0 kr ghost orders when API unavailable
  File: apps/web/src/app/(portal)/portal/bestallningar/page.tsx:39-43, 86-88, 145-151
        apps/api/src/routes/portal.ts:455-493
  Symptom: `CATALOG_FALLBACK_PRODUCTS` uses ids `"1"`, `"2"`, `"3"` (not UUIDs). If
  `/products` fails, user can submit; API skips unknown IDs (`continue`), inserts order
  with `totalOre: 0` and zero line rows.
  Root cause: Client fallback not aligned with server UUID validation; server accepts
  empty line arrays after skip loop.
  Fix: Disable submit when products not loaded from API; server reject when
  `lines.length === 0` or `totalOre === 0`; use real seed UUIDs in fallback or none.
  Effort: S
  Ref audit: CLUB_MEMBER [2.6] silent skip — STILL UNRESOLVED

[1.4] No delivery address, PO, or ship-to on B2B orders
  File: apps/api/src/routes/portal.ts:437-440 (body `{ items }` only)
        packages/db/src/schema/orders.ts:30-50 (no address columns)
        packages/db/src/schema/organizations.ts (no address book)
  Symptom: Wholesale buyer cannot specify delivery location, reference, or instructions.
  Order dialog collects qty only. Ops cannot fulfill without manual follow-up.
  Root cause: Order schema and CreateOrder contract never extended for B2B logistics.
  Fix: Add org delivery address (or address book), ship-to snapshot on order, optional
  PO/reference fields; collect in order dialog before POST.
  Effort: L
  Ref audit: CLUB_MEMBER [1.8], [1.10] — STILL UNRESOLVED

[1.5] Recurring / subscription orders — not implemented for clubs
  File: packages/db/src/schema/subscriptions.ts (sellerId/teamId/campaignId, no orgId)
        apps/web/src/app/(portal)/portal/* (no prenumeration route)
        apps/api/src/routes/portal.ts (no subscription endpoints)
  Symptom: Checklist item "set up, pause, cancel recurring orders" has zero surface.
  Subscriptions table targets supporter D2C flows, not org wholesale cadence.
  Root cause: Feature never scoped to B2B portal; AI copy references "kvartalsleverans"
  without backing data model.
  Fix: Add org-scoped subscription model (or reuse orders + cron), CRUD API, portal page
  with pause/cancel; wire dashboard `nextDelivery` from subscription schedule.
  Effort: L
  Ref audit: CLUB_MEMBER [1.3 area], [2.1] — STILL UNRESOLVED

[1.6] Invited club members cannot log in — no accept-invite flow
  File: apps/api/src/routes/portal.ts:744-748, 676-684
        apps/web/src/app/(portal)/portal/medlemmar/page.tsx:105-117
  Symptom: CLUB_ADMIN clicks "Skicka inbjudan" → row appears in table, toast success,
  **no email**. Invitee gets `passwordHash: invite-pending-{uuid}…` — login fails forever.
  Root cause: MVP defers token email; no accept-invite / set-password route (see Scout 11 [1.2]).
  Fix: Send invite email with token link; accept page sets password and creates session.
  Effort: M
  Ref audit: CLUB_MEMBER [1.13]; Scout 11 [1.2] — STILL UNRESOLVED

[1.7] Fortnox invoicing not wired for club B2B orders — fakturor page misleading
  File: apps/api/src/routes/portal.ts:470-495 (POST orders — no invoice trigger)
        apps/api/src/routes/fortnox-webhook.ts:68-72 ("Would update invoice status")
        apps/api/src/jobs/sync-invoice-status.ts (stub comments)
        apps/web/src/app/(portal)/portal/fakturor/page.tsx:6-11 (claims webhook mirror)
  Symptom: All club orders stay `invoiceStatus: NONE`, `fortnoxInvoiceId: null`. Fakturor
  UI promises Fortnox sync via webhook; webhook only logs. `getInvoiceProvider()` used
  on settlement/payout path only, not portal orders.
  Root cause: B2B invoice pipeline never connected end-to-end.
  Fix: On order confirm, create Fortnox invoice when org.fortnoxCustomerId set; webhook
  writes invoiceStatus; or honest UI copy until integration live.
  Effort: L
  Ref audit: CLUB_MEMBER [1.9] partial (UI exists, data never moves) — PARTIALLY FIXED UI ONLY

[1.8] Order list status mapping uses wrong field — tracking misleading
  File: apps/web/src/app/(portal)/portal/bestallningar/page.tsx:96-108
  Symptom: Maps `o.status === "PAID"` → "Levererad", but API `orders.status` enum is
  PENDING|CONFIRMED|SHIPPED|DELIVERED|CANCELLED — never PAID. `invoiceStatus` PAID is
  ignored. DELIVERED orders show "Under behandling". KPI cards count wrong buckets.
  Root cause: Confused fulfillment status with invoice status (April audit [1.11]).
  Fix: Map `order.status` to delivery labels; show `invoiceStatus` separately; fix KPI filters.
  Effort: S
  Ref audit: CLUB_MEMBER [1.11] — STILL UNRESOLVED
