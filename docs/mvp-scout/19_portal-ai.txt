SUMMARY
-------
Portal AI UI is materially improved since the April audit (role-specific welcome copy, CSRF, AbortController + stop button, unmount abort cleanup, SSE streaming with mid-stream error handling, disclaimer footer). The dominant MVP blocker remains architectural: the page still POSTs to `/v1/ai/public-chat` with `PUBLIC_CHAT_SYSTEM_PROMPT`, while the session-aware `/v1/ai/chat` route (role-based `buildSystemPrompt`, per-user rate limit, history sanitisation) is implemented but unused — `FEATURE_PORTAL_AI_SESSION_ENDPOINT` is not wired in web. Three fundraising roles (ASSOCIATION_ADMIN, TEAM_LEADER, SELLER) get internal-admin suggestion chips despite correct welcome text, creating false-confidence UX. Cross-links to `/portal/*` paths render as plain text; mobile keyboard and 429 retryAfter UX remain weak.
Findings: 18 (P1:4 P2:7 P3:4 P4:3)
MVP readiness: 58/100

P1 — CRITICAL (MVP-blocking)

[1.1] Portal AI still calls public endpoint — role-aware system prompt never applied
  File: apps/web/src/app/(portal)/portal/ai/page.tsx:18,124-136
  Symptom: Authenticated portal users POST to `/v1/ai/public-chat`. Server prepends `PUBLIC_CHAT_SYSTEM_PROMPT`, which explicitly refuses CRM/pipeline/admin answers (system-prompt.ts:57-58), while UI welcome/chips promise pipeline, KPI, and admin help.
  Root cause: MASTER_PLAN Fas 3 wiring not done. Session route `/v1/ai/chat` + `buildSystemPrompt(session.role)` exists in ai-chat.ts:126-136 but web never calls it. `flags.portalAiUseSessionEndpoint()` (flags.ts:72-76) is API-only — no web consumer.
  Fix: Point API_URL to `/v1/ai/chat`; gate rollout on `FEATURE_PORTAL_AI_SESSION_ENDPOINT` if desired. Remove dependency on PUBLIC_CHAT for logged-in surfaces.
  Effort: S
  Ref: AI_COACH [1.1], [1.4]; MASTER_PLAN Fas 3 item 209

[1.2] Wrong suggestion chips for ASSOCIATION_ADMIN, TEAM_LEADER, SELLER
  File: apps/web/src/app/(portal)/portal/ai/page.tsx:231-248
  Symptom: These roles get internal-admin chips ("Vilka KPI:er ska jag titta på idag?", "Systemstatus — kort sammanfattning", "Trender i håranalyskonvertering") while welcome text correctly targets campaign setup, team motivation, or shop sharing.
  Root cause: Ternary only branches CLUB_* and SALES_*; all other roles share default admin suggestions.
  Fix: Add explicit chip sets per ASSOCIATION_ADMIN, TEAM_LEADER, SELLER, INTERNAL_ADMIN (e.g. seller: "Hur delar jag min shop?", "Tips till vänner och familj", "Hur fungerar leveransen?").
  Effort: S
  Ref: AI_COACH [1.11] (welcome fixed; chips still broken)

[1.3] Sales-facing chips promise pipeline data the model cannot access
  File: apps/web/src/app/(portal)/portal/ai/page.tsx:238-242; public-chat.ts:77-80
  Symptom: Chip "Sammanfatta min pipeline" implies live CRM summary. Public prompt has no pipeline context and instructs refusal of CRM answers — high hallucination / false-confidence risk even after [1.1] fix unless copy is qualified.
  Root cause: Product copy ahead of backend grounding; no tools/RAG for pipeline data on any AI route.
  Fix: Reword chips to flow-level questions ("Hur fungerar pipeline i portalen?") until data grounding exists; in `buildSystemPrompt` SALES_* block, keep explicit "no database access — direct user to /portal/pipeline" (already partially present system-prompt.ts:68-69).
  Effort: S
  Ref: AI_COACH [1.3], [1.4]

[1.4] Per-user AI rate limit bypassed — portal shares anonymous IP bucket
  File: apps/web/src/app/(portal)/portal/ai/page.tsx:18; ai-chat.ts:84-92; public-chat.ts:18-20
  Symptom: Logged-in portal users hit `pub-chat:${ip}` (30/h per IP) instead of `aiRateLimit(session.userId)` (30/min per user). Shared office IP or NAT can block entire teams; conversely one user can consume shared quota.
  Root cause: [1.1] — wrong endpoint.
  Fix: Switch to `/v1/ai/chat` after [1.1]; optionally keep IP cap as secondary abuse guard on public-chat only.
  Effort: S (with [1.1])
  Ref: AI_COACH [1.9]

P2 — HIGH

[2.1] 429 rate-limit response ignores `retryAfter`
  File: apps/web/src/app/(portal)/portal/ai/page.tsx:139-144
  Symptom: Server returns `{ error, retryAfter }` (public-chat.ts:30-35; ai-chat.ts:86-91); client shows error string only — no countdown, disabled composer, or "försök om X min".
  Root cause: Generic `!res.ok` branch.
  Fix: Parse 429 body; disable input until window elapses; show formatted retry time.
  Effort: S
  Ref: Scout 6 [2.3]

[2.2] `/portal/*` paths in assistant replies are not clickable
  File: apps/web/src/app/(portal)/portal/ai/page.tsx:312-328
  Symptom: Model instructed to mention portal pages (system-prompt.ts:65-81) but bubbles render raw text — `/portal/pipeline` etc. are not links.
  Root cause: No markdown or safe URL linkification in message renderer.
  Fix: Lightweight link detector for `/portal/...` and known marketing paths → Next.js `<Link>`; or safe subset markdown.
  Effort: M
  Ref: MASTER_PLAN Fas 3 (portal navigation assist)

[2.3] Mobile soft keyboard likely obscures composer
  File: apps/web/src/app/(portal)/portal/ai/page.tsx:251,339-375
  Symptom: Fixed `h-[calc(100vh-8rem)]` layout inside portal shell (mobile header h-16 in layout.tsx). iOS/Android keyboard shrinks visual viewport; textarea at bottom may sit under keyboard; no `env(safe-area-inset-bottom)`.
  Root cause: CSS viewport units without `visualViewport` adjustment.
  Fix: Use `dvh` where supported; listen to `visualViewport` resize to scroll composer into view; add safe-area padding on input bar.
  Effort: M
  Ref: AI_COACH [3.2], [3.5]

[2.4] New conversation does not refocus input
  File: apps/web/src/app/(portal)/portal/ai/page.tsx:91-94 vs 87-89
  Symptom: After "Ny konversation", focus stays on button or last focused element; keyboard users must tab back to textarea.
  Root cause: `newConversation` omits `inputRef.current?.focus()`.
  Fix: Call focus after state reset (respect `streaming` guard — button already disabled while streaming).
  Effort: S

[2.5] No aria-live region for streamed assistant replies
  File: apps/web/src/app/(portal)/portal/ai/page.tsx:295-336
  Symptom: Screen readers not notified as tokens append during SSE.
  Root cause: Message list is static divs without `aria-live="polite"`.
  Fix: Wrap assistant message area in live region; use assertive for error bubbles.
  Effort: S
  Ref: Scout 6 [2.1]

[2.6] Message length mismatch — client allows >1000 chars to public-chat
  File: page.tsx (no client max); public-chat.ts:46-54 vs ai-chat.ts:102-107
  Symptom: User can type long messages; public endpoint rejects >1000 chars with 400; session route allows 2000. Confusing error once over limit.
  Root cause: No client-side maxlength aligned to active endpoint.
  Fix: Set `maxLength={2000}` on textarea when on `/chat`; validate before send with role-aware limit.
  Effort: S

[2.7] Redis rate limit fails open (affects current public-chat path)
  File: apps/api/src/lib/rate-limit.ts:29-31
  Symptom: Redis outage → unlimited AI requests on `/v1/ai/public-chat` (and `/v1/ai/chat` when wired).
  Root cause: `checkRateLimit` catch returns `{ allowed: true }`.
  Fix: Fail closed for AI keys or process-local fallback counter.
  Effort: M
  Ref: AI_COACH [1.8]; Scout 6 [1.1]

SECURITY NOTES
- Portal page is auth-gated by portal layout; API public-chat remains unauthenticated — any caller with CSRF can hit same endpoint without session (by design for marketing widget). Portal users should migrate to session-only `/v1/ai/chat` to avoid sharing anonymous abuse surface.
- Client history sends `{ role, content }` only (page.tsx:135) — good; server enforces user|assistant on both routes.
- User-typed content can still attempt prompt injection via message body and multi-turn history; BASE_RULES lack explicit anti-jailbreak clause (see Scout 6 [2.6]).
- `max_completion_tokens: 1024` and rate limits cap cost when Redis healthy.
