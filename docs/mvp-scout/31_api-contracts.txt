SUMMARY
-------
REST `/v1/*` errors are mostly consistent (`{ error: string }`, Swedish copy, sensible
401/403/404/409/429/500). Gaps are MVP-blocking for **multi-client correctness**: settlement
maps missing sessions to **403** (not 401), success envelopes mix `{ ok: true }` with bare
objects, **no machine-readable `code`**, **no `X-RateLimit-*` headers**, and **only portal
subset** is locked via `@roots/contracts` (offline Vitest — not runtime-validated on emit).
A parallel **tRPC** surface (`/trpc/*`) uses TRPCError codes + English messages; web
middleware still calls `trpc/auth.me` while product UI uses REST `/v1/auth/me`. `apiFetch`
swallows non-JSON error bodies to `{}`, so clients lose `error` text on proxy/HTML failures.

P1 — CRITICAL (MVP-blocking)

[1.1] No stable machine-readable error `code` on REST surface
  Files: all `apps/api/src/routes/*.ts`; `app.ts` onError (154-163)
  Symptom: Every failure is `{ error: "…" }` (Swedish prose only). Clients cannot branch on
  `CSRF_INVALID`, `RATE_LIMITED`, `ORG_MISSING` without string matching.
  Root cause: No shared `ApiError` helper or Zod error envelope in `@roots/contracts`.
  Fix: Add optional `code: z.string()` to a `apiErrorSchema`; map known cases in a small
  `jsonError(c, { error, code, status })` used by all routes + onError.
  Effort: M

[1.2] `settlement/*` returns 403 for unauthenticated callers (should be 401)
  File: apps/api/src/routes/settlement.ts:26-45,168-169,226-227
  Symptom: `requireAdmin()` returns `null` for missing cookie, expired session, OR wrong role;
  handler always `c.json({ error: "Behörighet saknas" }, 403)`.
  Root cause: Single null check conflates authn vs authz (same anti-pattern as pre-fix RBAC
  elsewhere).
  Fix: Split `requireSession` → 401 `"Ej inloggad"`, then role/org check → 403.
  Effort: S

[1.3] `@roots/contracts` not enforced at REST emit boundary (only offline tests)
  Files: packages/contracts/src/portal.ts; portal.contract.test.ts; portal.ts (no `.parse()`)
  Symptom: MASTER_PLAN T1 drift (UI keys vs API keys) can ship despite contracts existing;
  server never rejects its own malformed JSON before send.
  Root cause: Contract tests parse fixtures, not live handler output.
  Fix: In portal handlers (and shop snapshot paths), `dashboardResponseSchema.parse(payload)`
  before `c.json`, or shared `emitContract(c, schema, data)`.
  Effort: M

[1.4] Rate limits omit standard `X-RateLimit-*` / `Retry-After` headers
  Files: lib/rate-limit.ts; auth.ts:106-111; ai-chat.ts:86-91; public-chat.ts:30-35;
        hair-analysis.ts:84-87; contact.ts:35
  Symptom: 429 bodies sometimes include `retryAfter` (seconds) but no response headers;
  login/contact limits give only `{ error }`.
  Root cause: Rate limit helper returns in-memory counts, never sets Hono headers.
  Fix: Middleware or helper `applyRateLimitHeaders(c, result)` setting
  `Retry-After`, `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset`.
  Effort: S

[1.5] List endpoints use hardcoded caps without query pagination (except audit-log)
  Files: portal.ts (orders/quotes/clubs/pipeline limits 25–100); notifications.ts FEED_LIMIT;
        admin.ts:68-69 (GOOD: limit/offset/hasMore)
  Symptom: Sales/club portals silently truncate; no `?limit=&offset=` contract for integrators.
  Root cause: Performance guardrails baked in SQL `.limit(N)` without API params.
  Fix: Document defaults; accept `limit` (max cap) + `offset` on high-volume GETs; return
  `{ items, total, limit, offset, hasMore }` matching admin audit-log shape.
  Effort: M

P2 — HIGH

[2.1] Dual API: REST `/v1/*` + tRPC `/trpc/*` with incompatible error shapes
  Files: app.ts:131; trpc/handler.ts; trpc/routers/auth.ts:17-20 (English TOO_MANY_REQUESTS);
        web middleware.ts:119 (`/trpc/auth.me`)
  Symptom: Same domain (auth) exposes Swedish `{ error }` on REST and TRPC `{ code, message }`
  on tRPC; middleware uses tRPC while login page uses REST.
  Fix: Deprecate duplicate tRPC auth for web OR proxy tRPC errors to REST envelope at handler.
  Effort: L

[2.2] Success response envelope inconsistency (`ok` vs bare data)
  Files: auth.ts login `{ ok, user }`; portal create order `{ ok, order }`; contact/preview
        `{ ok: true }`; bankid `{ ok: false, error }`; most GETs return raw objects
  Symptom: Clients cannot assume `response.ok` or uniform success discriminator.
  Fix: Pick one pattern per API class (mutations → `{ ok: true, data }`, reads → resource) and
  document in contracts.
  Effort: M

[2.3] `apiFetch` masks failures when body is not JSON
  File: apps/web/src/lib/api.ts:39
  Symptom: `res.json().catch(() => ({}))` → `data.error` undefined; UI shows generic copy.
  Root cause: Defensive parse without `Content-Type` check or text fallback.
  Fix: If `!res.ok`, read `text()` when JSON parse fails; surface status in thrown Error.
  Effort: S

[2.4] `portalFetch` validates only `/v1/portal/*`; rest of app uses untyped `apiFetch`
  File: apps/web/src/lib/portal-api.ts
  Symptom: Dashboard fundraising (`/v1/dashboard/*`), shop, checkout, auth bypass contract
  validation — MASTER_PLAN field renames regress silently.
  Fix: Extend schema wrappers per domain package or OpenAPI-generated client.
  Effort: M

[2.5] AI streaming endpoints use a third contract (SSE JSON chunks, not `{ error }`)
  Files: ai-chat.ts, public-chat.ts; chat-widget.tsx / portal/ai/page.tsx
  Symptom: Non-stream errors use `{ error }`; stream uses `{ content }`, `[DONE]`, inline
  `parsed.error` — no shared type with REST.
  Fix: Document SSE event schema in contracts; align error event to `{ error, code? }`.
  Effort: M

[2.6] `GET /v1/shop/products` fail-open returns 200 with empty arrays on DB error
  File: apps/api/src/routes/shop.ts:125-137
  Symptom: Monitoring sees success; storefront shows empty catalog instead of 503.
  Fix: Log + return 500 `{ error }` (or degraded flag) like `by-slug`.
  Effort: S

[2.7] 401 copy inconsistent (`Ej inloggad` vs `Inte inloggad.`)
  Files: portal.ts, dashboard.ts, auth patterns vs ai-chat.ts:70
  Symptom: i18n/telemetry grouping harder; minor UX inconsistency.
  Fix: Single constant `AUTH_ERRORS.NOT_LOGGED_IN`.
  Effort: S

[2.8] `403` used for missing `orgId` (session valid, org null)
  Files: dashboard.ts:52; portal club guards
  Symptom: Demo/staging users hit "Behörighet" / "Ingen organisation" — clients treating 403 as
  role denial may mis-route (MASTER_PLAN demo orgId issue).
  Fix: Prefer 400 + `code: ORG_CONTEXT_REQUIRED` or 422; keep 403 strictly for role mismatch.
  Effort: S

[2.9] Validation never returns 422 — all semantic errors are 400
  Files: all routes (grep: no 422 in apps/api)
  Symptom: HTTP clients expecting RFC-style 422 for field validation cannot distinguish from
  malformed JSON (also 400).
  Fix: Optional: map Zod failures → 422 with `details[]` (additive to `error`).
  Effort: M

[2.10] Registration/auth REST ignores `@roots/contracts` Zod input schemas
  Files: packages/contracts/src/auth.ts; auth.ts manual checks
  Symptom: `RegisterAssociationSchema` etc. exist but routes duplicate ad-hoc validation →
  drift risk (min password rules, email format).
  Fix: `RegisterXxxSchema.safeParse(body)` at top of each POST.
  Effort: M
