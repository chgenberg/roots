  - Fragmented architecture: tRPC + TanStack Query + @roots/ui all declared but
    unused; useEffect data layer hand-rolled per page with inconsistent cancel
    guards; portal/fundraising shells fully client-rendered.

PRIORITY 1 — CRITICAL
=====================================================

[1.1] Settlement re-run overwrites payout amounts even when status is INVOICED or PAID
Agent: 7 — Fortnox & Commerce
File: apps/api/src/routes/settlement.ts
Line: 133–142
Detail: On re-generate, existing payout rows are updated with recalculated
  totalSalesOre, teamShareOre, and rootsShareOre with no guard on payout.status.
  A payout already invoiced in Fortnox or marked PAID can silently drift from the
  booked invoice and the amount actually transferred to the club. Fix: skip rows
  where status IN ('INVOICED','PAID') or fail the whole re-run if any are.

[1.2] `create-invoice` is not idempotent — retries create duplicate Fortnox invoices
Agent: 4 + 7 (independently flagged)
File: apps/api/src/routes/settlement.ts
Line: 299–415
Detail: Handler never checks payout.status === 'INVOICED' or an existing
  fortnoxInvoiceId before calling invoiceProvider.createInvoiceFromOrder.
  A timeout after Fortnox succeeds but before the DB update, or a double-click,
  produces a second invoice while only the latest ID is stored. Fix: gate on
  status + accept Idempotency-Key header, wrap external call in compensating tx.

[1.3] Klarna PAID transition never verifies charged amount matches order.totalOre
Agent: 7 — Fortnox & Commerce
File: apps/api/src/routes/checkout.ts
Line: 470–483, 533–538
Detail: Webhook and confirm-polling only check klarnaOrder.status ===
  'checkout_complete'. The response's order_amount is never compared to the DB
  row. Settlement later sums customerOrders.totalOre, so any Klarna-vs-Roots
  mismatch flows into payouts undetected. Fix: assert amount match before
  status transition; otherwise mark order REVIEW + alert ops.

[1.4] Klarna stub mode auto-completes every order when credentials are missing
Agent: 7 — Fortnox & Commerce
File: apps/api/src/lib/payments/klarna.ts
Line: 75–85, 121–130
Detail: When KLARNA_USERNAME/KLARNA_PASSWORD are unset, getCheckoutOrder always
  returns checkout_complete. Confirm-polling then marks any PENDING order PAID
  with no real payment. A prod misconfig (missing env vars) lets supporters reach
  PAID and enter settlement without money moving. Fix: stub must be gated on
  NODE_ENV !== 'production' AND require an explicit ROOTS_KLARNA_STUB=true flag.

[1.5] Unauthenticated /order-status/:orderId exposes full customer PII
Agent: 4 — Backend, API & Data
File: apps/api/src/routes/checkout.ts
Line: 589–637
Detail: GET /order-status/:orderId has no auth and returns customerName, line
  items, seller info, and order totals to anyone with the UUID. GDPR/privacy
  leak as soon as order IDs appear in URLs, logs, or referrer headers. Fix:
  bind to short-lived signed token issued at checkout creation, or require
  session match.

[1.6] Team-invite claim has TOCTOU race allowing double redemption
Agent: 4 — Backend, API & Data
File: apps/api/src/routes/association.ts
Line: 526–579
Detail: Invite validity (usedAt, expiry) checked outside the tx, and the in-tx
  UPDATE omits `WHERE used_at IS NULL`. Two concurrent POST /team-invites/claim
  with the same token can both create users/teams before either marks the
  invite used. Fix: single UPDATE … SET used_at = now() WHERE id = ? AND
  used_at IS NULL RETURNING …; treat zero rows as already claimed.

[1.7] Preview gate middleware falls back to hardcoded default password
Agent: 3 + 8 (independently flagged)
File: apps/web/src/middleware.ts (line 96); apps/api/src/lib/preview-gate.ts (22–25)
Detail: computePreviewToken() uses process.env.SITE_PREVIEW_PASSWORD || "Roots123%"
  when the env var is unset. A production deploy missing that variable gates
  the entire site behind a known, guessable password — and blocks SEO/crawlers.
  There is also no PREVIEW_GATE_DISABLED flag for launch. Fix: fail-closed if
  unset in prod; add explicit disable flag; rotate before public launch.

[1.8] Deletion cancel tokens can use a hardcoded dev HMAC secret in production
Agent: 8 — Security, DevOps & SEO
File: apps/api/src/lib/deletion-tokens.ts
Line: 30–38
Detail: getSecret() falls back to "roots-deletion-dev-secret-do-not-use-in-prod"
  when neither SESSION_SECRET nor DELETION_TOKEN_SECRET is set. validate-env.ts
  does not require either, so a misconfigured prod could mint/verify predictable
  cancel-deletion tokens. Anyone knowing the default could forge tokens and
  cancel other users' deletions. Fix: require boot validation; refuse to start.
