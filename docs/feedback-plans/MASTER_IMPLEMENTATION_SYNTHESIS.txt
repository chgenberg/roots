§13 SÄKER BYGGMODELL — "FÖRBÄTTRA ELLER LÅT VARA", ALDRIG TVINGA OM
================================================================================
Målet är att varje release antingen (a) **lämnar beteende identiskt** när flagga
av, eller (b) **förbättrar** mätbart (korrekta siffror, färre 500, tydligare UX)
utan att ta bort en fungerande väg.

§13.1 Strangler Fig / expand–contract (standard för all större förändring)
-------------------------------------------------------------------------
1. **Expand:** Lägg till nytt vid sidan av (nya kolumner, nya API-fält, ny route
   `/portal/insights` medan `/portal/statistik` lever kvar).
2. **Migrate:** Fyll data bakifrån (backfill-jobb, dubbel-skrivning kort period
   om nödvändigt — se §14.3).
3. **Contract:** När alla konsumenter läst nya fält/rutter, **deprecera** gamla
   fält i API (svara med båda en release), sedan ta bort i kod + UI sista steg.
4. **Never:** Bryt JSON-nycklar eller query-parametrar i samma PR som logikbyte
   utan mellanliggande "alias-release".

§13.2 Förbättring utan regression — accepterade förändringstyper
---------------------------------------------------------------
• **Bugfix** som gör att UI visar samma data API redan skickade = OK utan flagga.
• **Prestanda** (index, mindre JOIN) som inte ändrar svar = OK med benchmark i PR.
• **Säkerhet** (striktare validering, CSRF) som stoppar tidigare felaktiga requests
  = OK med tydlig release note; övervaka 4xx-spik.
• **Copy/tilgänglighet** som inte ändrar affärslogik = OK.

§13.3 När feature-flagga ALLTID krävs
--------------------------------------
• Ny navigation som flyttar användare mellan `/sales` och `/portal`.
• Ny obligatorisk validering på org (t.ex. segment NOT NULL) innan backfill klar.
• AI som ändrar persistens (auto-normalisera orgnamn vid save).
• Soft delete som döljer rader i listor.
• Settlement/payout-nyckelbyte (team → group_unit).

§14 KONTRAKTS- OCH SCHEMAREGLER (OPERATIONELLA)
================================================================================

§14.1 API: additivitet
----------------------
• **GET-respons:** nya fält ska vara **optional** i klienttyper; server ska alltid
  acceptera att gamla klienter ignorerar nycklar.
• **Breaking rename:** förbjud utan version `/v2/` eller parallell nyckel + en
  release med båda.
• **Portal-endpoints:** dela Zod-schema i `packages/` (eller motsvarande) så
  statistik, dashboard och framtida insights **importerar samma definition** —
  eliminerar T1 permanent.

§14.2 Databas: migrationsdisciplin
----------------------------------
• Endast **ADD COLUMN** / **CREATE INDEX CONCURRENTLY** / nya tabeller i samma
  release som kod som **inte kräver** kolumnen (nullable).
• **NOT NULL** + **SET NOT NULL** först när backfill = 100 % och verifierings-SQL
  grön i staging ≥ 48h.
• **ENUM-värden:** lägg alltid nytt värde sist; undvik att ändra betydelse av
  befintligt värde. Ny livscykel (t.ex. PACKED) = ADR + deploy-ordning: kod som
  förstår nya värdet **före** default som sätter det.
• **Triggers** (updated_at): introducera app-wide i små steg; verifiera att
  Drizzle `onUpdateNow()` inte dubblerar med DB-trigger.

§14.3 Denormaliserad data (org_id på customer_orders m.m.)
---------------------------------------------------------
Regel: **Skriv alltid org_id/group_unit_id från kanonisk källa vid transaktion**
(seller → team → org som idag). När nya FK tillkommer:
• I samma `INSERT`-transaktion: hämta seller + team + campaign och sätt alla
  konsistensfält; **DB CHECK** (valfritt) för `org_id = campaigns.org_id`.
• Backfill-jobb: idempotent `UPDATE … FROM` med LIMIT-batches; logga antal rader
  per körning; stoppa om avvikelse > 0.

§14.4 Läsning vs skrivning vid soft delete (07 + 02)
----------------------------------------------------
• **Fas A:** Lägg `deleted_at`, men **inga** default-filter i befintliga queries
  första release (ingen beteendeförändring).
• **Fas B:** Inför `withActive()` helper och använd i **nya** endpoints först.
• **Fas C:** Flytta befintliga list-endpoints en i taget med flagga per endpoint.
• **Fas D:** INTERNAL_ADMIN "papperskorg"-vy; först därefter global default-filter.
