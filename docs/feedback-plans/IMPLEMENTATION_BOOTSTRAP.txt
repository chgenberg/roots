15. **Bug-sweep pass 2 — master data + jobs contract**
    - **B5 (seed importer — dolt state via `any`-cast):**
      `buildSegmentCodeIndex` lagrade en collision-tracker som
      `(perName as any).__taken` på den interna Map:en. Bytt mot en ren
      side-table `takenByRiks: Map<string, Set<string>>`. Ingen `any`-cast,
      ingen läckande state-egenskap på publika maps.
    - **B6 (seed importer — duplicerade rader fick "-2"-suffix istället
      för identisk kod):** Om CSV:n råkade ha två rader med samma
      `(riksName, segmentName)` (t.ex. vid re-export från Excel) skulle
      den första raden få kod `"fotboll"`, den andra `"fotboll-2"`, och
      `perName.set` skrev över den första mappningens kod. Result vid
      iteration: båda raderna pekade på `"fotboll-2"` med samma namn → en
      enda rad i DB med fel kod. Fix: `if (perName.has(segName)) continue;`
      återanvänder befintlig kod för dubbletter. Riktiga slug-kollisioner
      (olika namn → samma slug, t.ex. `"Foo Bar"` vs `"Foo-Bar"`) får
      fortfarande `-2`-suffix.
    - **B7 (queue contract mismatch — `InMemoryQueue` vs `PgBossQueue`):**
      `InMemoryQueue` returnerade tidigare det **befintliga** jobb-id:t
      vid singleton-dedup. `PgBossQueue` (via pg-boss `send`) returnerar
      `null` när singleton-slot:en redan är upptagen. Två olika
      kontrakt → kod som litar på returvärdet skulle bytt beteende vid
      backend-byte. Fix: `InMemoryQueue` returnerar nu `null` vid aktiv
      singleton-slot och **frigör slot:en när jobbet drainats** (try/finally
      runt handler). Helt symmetriskt med pg-boss.
    - **Nya tester:**
        * 3 nya tester i `seed-masters/util.test.ts`:
          – återanvänder samma kod för duplicerade (riks, segment)-rader.
          – `-2`-suffix på riktiga slug-kollisioner.
          – kod-namespaces är isolerade per riks (samma segmentnamn under
            två riks → samma kod, ingen kollision).
        * Befintliga `queue.test.ts` "deduplicates by singletonKey"-testet
          uppgraderat: kör med blockerad handler (Promise.gate) för att
          bevisa att andra enqueue inom aktiv slot returnerar `null`, och
          att tredje enqueue **efter** drain får en fräsch id.
    - **Granskade men inga buggar:**
        * Migrations 0002/0003 — idempotent, FK-namnen matchar Drizzle:s
          auto-naming, indexes täcker schemat.
        * `organizations.assignedAsmUserId` saknar Drizzle `.references()`
          men FK skapas i SQL — medveten trade-off för att undvika cyklisk
          import med `users.ts`. Dokumenterad i schema-header.
        * `dashboardResponseSchema.stats` använder `z.union` istället för
          `z.discriminatedUnion` — fungerar via disjoint nycklar, men
          långsammare. Ej buggfix idag (additivt API-brott krävs).
        * `parseCsv` hanterar inte newlines i citerade celler — dokumenterat
          i kodkommentar, OK för våra master-CSV:er.
        * `MockDb.chain` är en delad Proxy — parallella `Promise.all` på

19. **DEPLOY-AUTOMATION — migrate-on-boot + worker-image** (det här steget)
    Mål: möjliggöra att den nyss pushade Fas 1-koden (master-data v1 +
    organization-normalize-agenten) faktiskt kan rullas ut i produktion
    utan manuell `drizzle-kit migrate` på DB-värden och utan separat
    worker-byggpipeline.

    - **`packages/db/src/migrate.ts`** (ny):
        * `runMigrations({ databaseUrl?, migrationsFolder?, lockTimeoutMs? })`
          – dedikerad single-connection `postgres-js`-klient (separat från
          långlivade pool:en i `client.ts`).
          – wrappar `drizzle migrate()` i `pg_advisory_lock(hashtext('roots_migrator_v1'))`
          så fler API/worker-instanser kan boota samtidigt – en kör, andra
          väntar och no-op:ar efteråt.
          – returnerar `{ applied, finalCount, durationMs }` (mäter genom
          räkning av `drizzle.__drizzle_migrations` före/efter).
          – resolvar migrations-mappen från (1) argument, (2)
          `MIGRATIONS_FOLDER` env, (3) `<dirname>/../drizzle` (dev), (4)
          `<cwd>/drizzle` (Docker runtime).
    - **`packages/db/src/index.ts`** re-exporterar `runMigrations` +
      typer så `apps/api` och framtida CLI-verktyg slipper djupimporter.
    - **`apps/api/src/lib/migrate-on-boot.ts`** (ny):
        * `runBootMigrations()` gated bakom `RUN_MIGRATIONS_ON_BOOT`
          (default: off → ingen beteendeförändring för existerande deploys).
        * No-op om `DATABASE_URL` saknas (defensiv).
        * Migration-fel = **fatalt** → re-throws så orchestratorn (Docker /
          Railway / Fly) markerar deployen ond. Säkrare än att starta API
          mot schema-inkompatibel DB.
        * `MIGRATE_LOCK_TIMEOUT_MS` (default 60s) skickas vidare till
          `runMigrations()` → kort wait om annan instans håller låset.
    - **Hookas in på boot:**
        * `apps/api/src/index.ts` → `await runBootMigrations()` **före**
          `serve()` så HTTP-trafik aldrig accepteras mot fel schema.
        * `apps/api/src/workers/index.ts` → samma anrop före
          `startWorkers()`. Säker pga advisory-låset (race med API:n no-op:ar).
    - **`apps/api/src/lib/migrate-on-boot.test.ts`** (6 tester):
        * No-op om flag unset/false.
        * Kör om flag truthy + `DATABASE_URL` finns.
        * No-op (inte throw) om `DATABASE_URL` saknas.
        * Re-throws migration-fel.
        * Forwardar `MIGRATE_LOCK_TIMEOUT_MS`.
    - **`apps/api/tsup.config.ts`** unifierad till en enda källa:
        * `entry: ["src/index.ts", "src/workers/index.ts"]` — bygger **båda**
          bundlarna med samma kommando.
        * `format: ["cjs"]` matchar Dockerfile:s `node dist/index.js` (och
          `dist/workers/index.js`).
        * `dts: false` — sparade ~49s på cold-build i CI; `pnpm typecheck`
          står för typkontrollen ändå.
    - **`apps/api/package.json`**: `build` förenklat till `tsup` (inga
      CLI-args som krockar med configen).
    - **`apps/api/Dockerfile`** (runtime-stage):
        * Kopierar `packages/db/drizzle` → `/app/drizzle` i runtime-imagen.
        * Kopierar `packages/db/data` → `/app/data` för ad-hoc seed-körningar.
        * `ENV MIGRATIONS_FOLDER=/app/drizzle` — explicit, ingen tvetydighet.
        * CMD oförändrad (`node dist/index.js`); kommentar tillagd att
          workers återanvänder samma image via `command:`-override.
    - **`docker-compose.yml`**:
        * Ny `workers`-service som bygger **samma** image som `api` men
          startas med `command: ["node","dist/workers/index.js"]`. Slipper
          en parallell byggpipeline.
        * `api` får `RUN_MIGRATIONS_ON_BOOT=true` (äger schemat).
        * `workers` får `RUN_MIGRATIONS_ON_BOOT=false` + `WORKERS_ENABLED=true`
          och `depends_on: api: service_started` så API:n hinner låsa och
          köra eventuella migrations först. Advisory-låset är säkerheten
          om ordningen ändå skulle byta plats.
    - **Resultat:** 83 tester gröna över hela monorepot (20 db + 63 api),
      `pnpm --filter @roots/api build` producerar både `dist/index.js`
      (224 KB CJS) och `dist/workers/index.js` (51 KB CJS) på <100 ms.
      Ingen ändring i affärslogik.

20. **PROD-ROLLOUT — schema-journal-fix + auth-fallback-härdning**
    Mål: faktiskt aktivera Fas 1 i Railway-produktion.

    - **Upptäckt schema-drift**: prod-DB:n hade ursprungligen provisionerats
      via `drizzle-kit push`, så alla tabeller från 0000_premium_photon
      fanns, men `drizzle.__drizzle_migrations`-journalen var tom.
      Migrate-on-boot trodde därför att 0000 aldrig kört → försökte skapa
      enum:en `user_role` igen → `type already exists` → healthcheck-fail.
      Eftersom migrate-on-boot är fail-fast (re-throw) avvisade
      orchestratorn deployen — bra design, men prod var fast i en gammal
      container utan kolumnerna från 0001–0003.
    - **Auth-fallback-bugg blottad samtidigt**: `apps/api/src/routes/auth.ts`
      hade `try { db.select... } catch { return 401 }` som slukade DB-fel
      i tystnad. När `users.birth_year` saknades (0001 ej kört) returnerade
      varje login 401 *innan* in-memory-demo-fallbacken hann triggas.
      Detta gjorde att `ROOTS_ENABLE_DEMO_ACCOUNTS=true` inte räckte för
      att logga in i prod när schemat hade drift.
        * Fix (commit `5978b7e`): `try`-blocket loggar nu felet via
          `log.warn({ err, ... }, "DB user lookup failed during login —
          falling back to demo accounts")` och **faller igenom** till
          demo-blocket istället för att returnera 401. Sekundär
          `organizations`-uppslagning fick eget try/catch så att en
          partiellt migrerad org-tabell inte heller dödar inloggningen.
        * Tester: 63/63 grön. Snapshots oförändrade (demo-flödet är
          inte täckt av snapshots → ingen drift).
    - **Journal-seed mot prod** (engångsåtgärd):
        1. `node` lokal helper läste alla migrations-filer och beräknade
           SHA-256-hashar (samma algoritm som drizzles `readMigrationFiles`).
        2. `psql` via Railway:s public TCP proxy (junction.proxy.rlwy.net:52526):
           ```sql
           INSERT INTO drizzle.__drizzle_migrations (hash, created_at)
           VALUES ('8477b88456bd…1b9f', 1775387675375);
           ```
           Markerade endast **0000** som applicerad — eftersom 0001–0003
           alla är `IF NOT EXISTS`-baserade kunde de köras säkert av nästa
           migrate-on-boot.
    - **Aktiverad rollout**:
        * `RUN_MIGRATIONS_ON_BOOT=true` på `roots`-servicen → boot körde
          0001, 0002, 0003 utan fel → journalen har nu 4 rader.
        * Verifierat schema: `users.birth_year/guardian_user_id/
          guardian_consent_at` finns, `organizations` har alla 9 nya
          masterdata-kolumner, `master_riksorganisation` + `master_segment`
          tabellerna finns.
        * `ROOTS_ENABLE_DEMO_ACCOUNTS=true` → demo-login funkar
          (`salj@roots.se / Demo1234!` returnerar 200 med korrekt role +
          orgName).
    - **Fortfarande av i prod**:
        * `FEATURE_NEW_ORG_HIERARCHY` — schemat finns men master-tabellerna
          är tomma. Slå inte på förrän `db:seed:masters` körts mot prod-DB
          (alternativ: in-DB upsert via UI när admin-vy från skill 01
          plan 07 landar).
        * `WORKERS_ENABLED` — `workers`-servicen finns i `docker-compose.yml`
          men inget motsvarande Railway-service är skapat. Lägg till manuellt
          via Railway UI eller via `railway add` när org-normalizer-agentens
          batch-körning behövs.
